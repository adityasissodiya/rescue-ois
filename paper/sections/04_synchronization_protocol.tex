\section{Synchronization Protocol}
\label{sec:sync}

The protocol design follows from the requirements and constraints in Section~\ref{sec:requirements}. Outbox durability at responder vehicles and tablets supports R2; sequence assignment by the command vehicle aligns the storage authority boundary with R3; and responders mark outbox entries forwarded only after acknowledgement from the command writer. The role asymmetry below --- command commits, responder forwards, tablet submits --- is the design point adopted for this operational setting, not a claim that no other protocol structure could satisfy related requirements.

\subsection{Baseline Sync}

Baseline synchronization distributes master data from the core to vehicle edge nodes using one-way replication and package pulls. In the target design, logical replication can handle database schemas suited to that model, while heavier artifacts such as tiles and attachments are published as versioned bundles with signed or hashed manifests. The reported emulation exercises a synthetic bootstrap endpoint rather than the full logical-replication and package-publisher path.

\subsection{Incident Bootstrap}

On dispatch, the target protocol has the core prepare an incident-specific package consisting of the area of interest, referenced attachments, and an initial manifest. The command vehicle attempts to pull this package from the core first. Responder vehicles then either pull directly from core or bootstrap from the command node over the mesh if WAN access is absent. Tablets bootstrap only from their local vehicle node.

Command backhaul to the regional core is a later cursor-based step when WAN connectivity is present.

\subsection{Protocol Contract}
\label{sec:protocol-contract}

The repository prototype implements the core idempotency path using \texttt{incident\_id} and \texttt{client\_event\_id}. The intended contract is:
\begin{itemize}
  \item \textbf{Identity.} Each submission has a globally unique idempotency key, \texttt{client\_event\_id}, scoped by the incident and originating client identity.
  \item \textbf{Durable local acceptance.} A responder accepts a submission only after the event is stored in its local outbox. In the present evaluation, the Python tablet stub posts directly to the responder API; Android-side local persistence is not exercised.
  \item \textbf{Command commit.} The command node accepts a \texttt{client\_event\_id} once, assigns \texttt{event\_seq} atomically with journal insertion, and maps duplicates to the existing journal entry rather than resequencing them.
  \item \textbf{Forwarding acknowledgement.} A responder may mark an outbox item forwarded only after the command writer acknowledges durable journal acceptance or duplicate recognition.
  \item \textbf{Catch-up.} Consumers apply committed journal entries in \texttt{event\_seq} order after their last applied sequence. Materialized state is derived from the journal and can be rebuilt.
  \item \textbf{Authority.} The command-side journal is authoritative for incident decisions. Responder outboxes, tablet caches, and materialized views are derived or pending state.
\end{itemize}

The current schema does not yet include a stored \texttt{command\_epoch}; promotion epochs and fencing are specified below as protocol design and model-level validation rather than as a fully implemented production path.

\subsection{Partition Behavior}

Partition handling is intentionally asymmetric, reflecting the tiered authority model:
\begin{itemize}
  \item If a responder loses mesh connectivity to command, tablets continue to operate from cache and local outbox entries accumulate until reconnection.
  \item If the command vehicle loses WAN connectivity to core, local incident operations continue and the journal backfills upstream later.
  \item If the command vehicle is lost, a responder is promoted manually and becomes the new single writer for the incident.
\end{itemize}

\subsection{Command Promotion, Epochs, and Fencing}
\label{sec:promotion}

The design does not provide automatic failover. It chooses operator-confirmed promotion and fencing to preserve command authority and avoid implicit split brain. Figure~\ref{fig:promotion-fencing} summarizes the intended production rule: each command tenure has a monotonically increasing epoch or equivalent term, promotion emits an explicit record, and stale command traffic is rejected once a newer epoch is known.

This strict rule sacrifices availability when the previous command cannot be fenced or its status cannot be established. The TLA+ model captures the same safety boundary abstractly: strict promotion revokes the previous authority and refreshes the promoted node's cursor, while weak promotion leaves an unreachable previous authority active and produces split-brain counterexamples. The prototype includes an interactive \texttt{promote-responder.sh} script and model-level validation, but not durable command epochs, automatic stale-epoch rejection, or crash-validated fencing in the running services.

\subsection{Consistency Guarantees}

The protocol provides the following consistency guarantees:
\begin{itemize}
  \item The incident journal is totally ordered because only one command node commits events at a time.
  \item Outbox delivery from responders is at least once and must be deduplicated by durable event identifiers.
  \item Master data converges eventually from core to edge.
  \item Tablets converge eventually with their local vehicle edge.
  \item There is no claim of causal ordering across independent responder outboxes before command assignment.
\end{itemize}

These guarantees hold under the assumption that at most one command node is active per incident at any time and that stale command tenures are fenced before a promoted node accepts authority-bearing commits. Weak promotion is deliberately excluded; it is the counterexample case used in Section~\ref{sec:eval-safety}.
