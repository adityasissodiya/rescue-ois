\section{Synchronization Protocol}
\label{sec:sync}

The protocol maps the roles and state classes from
Section~\ref{sec:problem-analysis} to three paths: baseline sync, field-event
forwarding, and command promotion. The main identifiers are
\textit{incident\_id}, a client-supplied \textit{client\_event\_id}, and a
command-assigned \textit{event\_seq}. The promotion model also uses a command
epoch or equivalent term.

\subsection{Baseline Sync}

Baseline synchronization distributes master data from the core to vehicle edge
nodes using one-way replication and package pulls. In the target design, logical
replication handles schemas suited to that model. Heavier artifacts, such as
tiles and attachments, are published as versioned bundles with signed or hashed
manifests. The reported emulation exercises a synthetic bootstrap endpoint. It
does not exercise the full logical-replication or package-publisher path.

\subsection{Incident Bootstrap}

On dispatch, the target protocol has the core prepare an incident-specific
package. The package contains the area of interest, referenced attachments, and
an initial manifest. The command vehicle tries to pull this package from the
core first. Responder vehicles then either pull from core or bootstrap from the
command node if WAN access is absent. Tablets bootstrap only from their local
vehicle node.

\subsection{Field Edit Flow}

Figure~\ref{fig:outbox-sequence} shows the steady-state field edit path. The
boundary is between local durability and authoritative command commit.
A responder may acknowledge local acceptance after the outbox insert. It marks
an item forwarded only after command-side journal acceptance or duplicate
recognition. Command backhaul to the regional core is a later cursor-based step
when WAN connectivity is present.

\subsection{Protocol Contract}
\label{sec:protocol-contract}

The repository prototype implements the core idempotency path using
\textit{incident\_id} and \textit{client\_event\_id}. The intended contract is:
\begin{itemize}
  \item Each submission has a globally unique idempotency key, \textit{client\_event\_id}, scoped by the incident and originating client identity.
  \item A responder accepts a submission only after the event is stored in its local outbox.
  \item The command node accepts a \textit{client\_event\_id} once and assigns \textit{event\_seq} atomically with journal insertion. It maps duplicates to the existing journal entry rather than resequencing them.
  \item A responder may mark an outbox item forwarded only after the command writer acknowledges durable journal acceptance or duplicate recognition.
  \item Consumers apply committed journal entries in \textit{event\_seq} order after their last applied sequence. Materialized state is derived from the journal and can be rebuilt.
  \item The command-side journal is authoritative for incident decisions. Responder outboxes, tablet caches, and materialized views are derived or pending state.
\end{itemize}

The current schema does not yet include a stored \textit{command\_epoch}; Section~\ref{sec:implementation} records that implementation boundary.

The safety properties are single authority for \textit{event\_seq} assignment,
no forked journal under the strict promotion rule, and idempotent replay by
\textit{client\_event\_id}. The progress assumptions are bounded.
Command-local progress requires the command service and its local storage.
Responder partitions defer responder-originated authoritative acceptance.
Promotion is manual and fenced.

\subsection{Partition Behavior}

Partitions follow the tiered authority model:
\begin{itemize}
  \item If a responder loses mesh connectivity to command, tablets continue from cache and local outbox entries accumulate until reconnection.
  \item If the command vehicle loses WAN connectivity to core, local incident operations continue and the journal backfills upstream later.
  \item If the command vehicle is lost, a responder can become command only through explicit promotion and fencing of stale authority.
\end{itemize}

\subsection{Command Promotion, Epochs, and Fencing}
\label{sec:promotion}

The design does not provide autonomous failover. An operator confirms promotion,
and fencing prevents stale command authority from continuing.
Figure~\ref{fig:promotion-fencing} summarizes the intended rule. Each command
tenure has a monotonically increasing epoch or equivalent term. Promotion emits
an explicit record. Stale command traffic must be rejected once a newer epoch is
known. The running services do not yet implement durable epoch storage or
stale-epoch rejection. Those pieces remain protocol/model requirements and
future implementation work.

This strict rule sacrifices availability when the previous command cannot be
fenced or its status cannot be established. Section~\ref{sec:eval-safety}
checks this boundary by comparing strict promotion with a weak variant.

\subsection{Consistency Guarantees}

The protocol provides the following consistency guarantees:
\begin{itemize}
  \item The incident journal is totally ordered because only one command node commits events at a time.
  \item Outbox delivery from responders is at least once and must be deduplicated by durable event identifiers.
  \item Master data converges eventually from core to edge.
  \item Tablets converge eventually with their local vehicle edge.
  \item There is no claim of causal ordering across independent responder outboxes before command assignment.
\end{itemize}

These guarantees depend on the promotion rule in Section~\ref{sec:promotion}.
The prototype evaluates the implemented idempotency, outbox, sequencing, and
forwarding paths. The epoch/fencing rule is evaluated only at model level.
