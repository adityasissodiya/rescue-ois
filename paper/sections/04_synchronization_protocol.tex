The main identifiers are
\textit{incident\_id}, a client-supplied \textit{client\_event\_id}, and a
command-assigned \textit{event\_seq}. The promotion model also uses a command
epoch or equivalent term.

\subsection{Authority Boundary (M1)}
\label{sec:protocol-m1}

M1 makes precise the state-contract distinction introduced in
Section~\ref{sec:state-taxonomy}: which operations require linearization at the
command, and which use weaker contracts. The command-side journal is
authoritative for incident decisions. Responder outboxes, tablet caches, and
materialized views are derived or pending state. The single-writer rule applies
only to authority-bearing incident-journal entries; master/reference data,
local field submissions before command acceptance, and materialized projections
use the weaker contracts summarized in Figure~\ref{fig:state-contracts}.

\subsection{Command Journal Sequencing (M2)}
\label{sec:protocol-m2}

M2 specifies how the command authority linearizes authority-bearing operations
into a totally ordered journal. The command node accepts a
\textit{client\_event\_id} once and assigns \textit{event\_seq} atomically with
journal insertion. It maps duplicates to the existing journal entry rather than
resequencing them. Consumers apply committed journal entries in
\textit{event\_seq} order after their last applied sequence; materialized state
is derived from the journal and can be rebuilt.

\subsection{Durable Outbox and Idempotent Submission (M3)}
\label{sec:protocol-m3}

M3 specifies the responder-side path for non-authority data: locally durable,
idempotent, and eventually forwarded to the command journal.
Figure~\ref{fig:outbox-sequence} shows the steady-state field edit path. The
boundary is between local durability and authoritative command commit. A
responder may acknowledge local acceptance after the outbox insert. It marks
an item forwarded only after command-side journal acceptance or duplicate
recognition.

\begin{figure}[t]
\centering
\input{figures/fig_outbox_sequence}
\caption{Responder outbox protocol. A tablet submission is acknowledged locally only after durable outbox insertion. The command journal later assigns the authoritative sequence number, and duplicate delivery is handled by \textit{client\_event\_id}.}
\label{fig:outbox-sequence}
\end{figure}

The M3 contract has three parts:
\begin{itemize}
  \item Each submission has a globally unique idempotency key, \textit{client\_event\_id}, scoped by the incident and originating client identity.
  \item A responder accepts a submission only after the event is stored in its local outbox.
  \item A responder may mark an outbox item forwarded only after the command writer acknowledges durable journal acceptance or duplicate recognition.
\end{itemize}

Outbox delivery from responders is at least once and must be deduplicated by
durable event identifiers at the command. There is no claim of causal ordering
across independent responder outboxes before command assignment.

\subsection{Fenced Promotion (M4)}
\label{sec:protocol-m4}

M4 specifies how command authority is transferred between vehicles without
forking the journal. The design does not provide autonomous failover. An
operator confirms promotion, and fencing prevents stale command authority from
continuing. Figure~\ref{fig:promotion-fencing} summarizes the intended rule.
Each command tenure has a monotonically increasing epoch or equivalent term.
Promotion emits an explicit record. Stale command traffic must be rejected once
a newer epoch is known. Section~\ref{sec:eval-m4} reports the service-path
measurement of this rule.

\begin{figure}[t]
\centering
\input{figures/fig_promotion_fencing}
\caption{Promotion preserves the single-writer invariant only under strict fencing. The figure summarizes the protocol requirement and the weak-promotion counterexample.}
\label{fig:promotion-fencing}
\end{figure}

This strict rule sacrifices availability when the previous command cannot be
fenced or its status cannot be established. Section~\ref{sec:eval-m4}
checks this boundary by comparing strict promotion with a weak variant.

The safety properties are single authority for \textit{event\_seq} assignment,
no forked journal under the strict promotion rule, and idempotent replay by
\textit{client\_event\_id}. The progress assumptions are bounded:
command-local progress requires the command service and its local storage;
responder partitions defer responder-originated authoritative acceptance;
promotion is manual and fenced.

\subsection{Partition Behavior and Cross-Cutting Paths}
\label{sec:protocol-partition}

This subsection summarizes how the four mechanisms interact under network
partition, and gathers the cross-cutting paths (baseline master-data
distribution, incident bootstrap, command-to-core backhaul) that lie outside
the authority-aligned contribution.

Baseline master-data distribution from the regional core to vehicle edges uses
one-way replication and package pulls; this path is outside the authority-aligned
contribution and we do not evaluate it. Incident bootstrap, in which the core
prepares an incident-specific package on dispatch, is similarly out of scope as a
contribution; we describe both paths only to position the authority-bearing
mechanisms (M1--M4) against the rest of the system surface.

Partitions follow the tiered authority model:
\begin{itemize}
  \item If a responder loses mesh connectivity to command, tablets continue from cache and local outbox entries accumulate until reconnection.
  \item If the command vehicle loses WAN connectivity to core, local incident operations continue and the journal backfills upstream later.
  \item If the command vehicle is lost, a responder can become command only through explicit promotion and fencing of stale authority.
\end{itemize}

Command-to-core backhaul is cursor-based and runs whenever the command vehicle
has WAN connectivity to the regional core; it carries committed journal
entries forward without changing their assigned \textit{event\_seq}. Master
data converges eventually from core to edge, and tablets converge eventually
with their local vehicle edge. The current schema records command epochs
durably (Section~\ref{sec:implementation}); the prototype evaluates the
implemented idempotency, outbox, sequencing, forwarding, and epoch-fencing
paths.
