\section{Problem Analysis}
\label{sec:problem-analysis}

\subsection{Operational Setting}

The target setting is municipal rescue-service incident response. A regional
core supports dispatch, reference data, and backhaul; vehicle edge nodes run
near the incident site; field tablets attach to a local vehicle and act as leaf
clients. Connectivity is intermittent: vehicles may move between wide-area
connectivity, mesh-only contact, and total
isolation~\cite{zimbelman2022mesh,wang2023overview}. One vehicle edge node holds
the command role for the incident; we call it the command edge. The role can move to another vehicle,
but only through an explicit human decision, and the protocol must respect that
operational authority. Figure~\ref{fig:op-setting} illustrates the actors and the three
connectivity regimes.

\subsection{Position Relative to Consensus, CRDTs, and Emergency Networking}

\systemname{} recombines
well-known mechanisms (single-leader
replication, transactional outbox~\cite{richardson2018microservices},
idempotency keys, manual fencing) under a domain-specific rule; the
incident-journal linearization point is the command edge, set by an
external operational protocol rather than chosen by liveness-driven leader
election. The incident-state entity owns its decision history; external
actors interact through forward-only events rather than mutate state
directly~\cite{helland2017life}. The novelty is therefore in (i) which
operations are placed under that linearization point and which are not, and
(ii) the fenced-promotion rule that preserves single-authority across command
changes. The mechanisms themselves are not claimed as novel.

Existing systems solve adjacent parts of the problem---offline-first stores,
conflict-free replicated data types (CRDTs), consensus logs, and emergency/edge
networking---but none, by itself, states which rescue-service actor may issue
non-commutative command decisions during a partition.

Offline-first and local-first systems prioritize local availability and
continued operation under poor connectivity~\cite{kleppmann2019localfirst,paul2019crimp,kleppmann2017ddia,richardson2018microservices},
and CRDT and strong-eventual-consistency work---including richer local-first
safety models and Hanssen's CRDT replication for emergency management, our
closest baseline---provides convergence for mergeable replicated
state~\cite{almeida2014delta,gomes2017verifyingsec,haas2023lore,kohler2025consistent,jannes2021owebsync,lewchenko2025boltonsc,hanssen2025emergency}.
Consensus, shared-log, and chain-replication systems provide replicated
agreement and ordered logs under their stated failure
models~\cite{lamport1998parttime,ongaro2014raft,balakrishnan2013tango,katsarakis2020hermes,liang2025holipaxos,gooding2025lark,vanrenesse2004chain}.
These help responders keep working or order writes, but none decides \emph{which
actor} may issue an authority-bearing decision. \systemname{} keeps
authority-bearing events under the incident-journal sequencer, treats outbox
entries as pending until command acceptance, and assigns weaker contracts to
non-authority data.

Closest in setting is emergency and edge networking. CoNICE~\cite{jahanian2022conice}
reaches agreement among infrastructure-less peers under intermittent
connectivity using One-Third-Rule consensus, evaluated on shared map-pin
updates; it is the right tool when no peer is privileged, whereas
rescue-service incident command has a designated commander at every moment and
the network is not allowed to vote on incident decisions. Public-safety
networking and edge/fog research place resilient transport and storage near
responders~\cite{kumbhar2015legacy,wang2023overview,sagor2024distressnetng,aboualola2023edgesurvey}.
We are not aware of prior work that explicitly uses operational command
authority as the linearization boundary while assigning weaker contracts to
non-authority incident data; \systemname{} aligns the incident-journal
linearization point with the current operational command authority and uses
fenced promotion rather than leader election for command transfer.

\subsection{Requirements and Assumptions}
\label{sec:requirements}

Public rescue-service guidance and studies of Swedish rescue-service information
systems motivate the requirements used here~\cite{rsg-rad201,rsg-kommunalplan,pilemalm2014enabling,westman2021mobilisation}.
The requirements are separate from the architecture. In particular,
attributable command authority does not logically require a single-writer
database design. Aligning the incident-journal linearization boundary with command authority
is the design choice made in this paper.

The externally motivated requirements are:
\begin{itemize}
  \item \textbf{\textit{R1 (Offline operation)}} Each tier must keep working from
  previously synchronized data without continuous connectivity.
  \item \textbf{\textit{R2 (Durable forward-only submission)}} Field submissions entered
  on tablets must survive vehicle restart and prolonged partition.
  \item \textbf{\textit{R3 (Attributable command authority)}} Resource assignments,
  status transitions, and hazard annotations must be attributable to one
  operational command authority at any instant.
\end{itemize}

The design assumes that an incident has one current command authority. The
command role is fixed at dispatch and changes only through an explicit operator
decision. The deployment constraints are separate: the mesh should act as routed
transit rather than a stretched user network, and the system must reuse the
rescue-service identity infrastructure. Their architectural consequences---edge
cache and local services, tablet/edge outbox and retry, a single
incident-journal writer, mesh-as-transit routing, and mTLS/CA identity
integration---are developed in \S\ref{sec:architecture}.
