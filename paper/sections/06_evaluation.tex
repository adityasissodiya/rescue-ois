\section{Evaluation}
\label{sec:evaluation}
\label{sec:validation}

\subsection{Emulation Environment}
\label{sec:eval-env}

All measurements reported in this section come from a Docker Compose
emulation: one regional core, one command-role edge node, and three
responder-role edge nodes as separate Compose projects sharing a single
Docker bridge network with plain-HTTP container traffic. Synthetic field
events are submitted through a Python tablet stub. WAN partitions are
injected by disconnecting and re-attaching containers from the bridge
network with the original DNS aliases preserved. Each measured scenario
cell repeats $N=30$ times unless otherwise noted; we report median and
95th-percentile values.

The primary metrics file contains 390 records:
120 bootstrap-latency records, 90 field-edit propagation records, 90
WAN-recovery records, 30 throughput records, 30 duplicate-replay records,
and 30 explicit ``skipped'' command-promotion records. The Raft metrics
file contains 160 measured baseline records. The harness records scenario
parameters, timestamps, and outcomes for each run.

\subsection{Authority Boundary Evidence (M1)}
\label{sec:eval-m1}

This subsection reports the evidence for M1 (authority boundary) and M2
(command journal sequencing): writes commit on the command's authority path
even when responders are isolated, and the serialization point characterizes
the cost of single-writer journaling.

\textbf{Direct command commit during responder isolation.}
The \texttt{evaluate-command-local-partition.py} harness isolates one
responder \textit{syncd} from the command edge for ten seconds and, during
the partition, issues 20 single-event POSTs directly to the command
\texttt{/accept/event-batch} endpoint. All 20/20 attempts commit (HTTP~200,
contiguous \texttt{event\_seq}) with no responder reachable, confirming that
the M1 authority boundary keeps the command-side write path available under
responder partition. Per-attempt commit latency has a median of $\sim$2.8\,ms
and p95 $\sim$7.1\,ms. The tablet-facing command \textit{ops-api} is not
exercised here.

\textbf{Steady-state throughput.}
We saturate the command edge with 1000 concurrent submissions per run and
measure end-to-end commit rate. The first run of each pass exhibits a
documented warm-up artefact ($\sim$54 ev/s) from connection-pool
establishment and JIT optimisation; we exclude \texttt{run\_index = 0}.
Across the remaining 29 runs, the command edge sustains a median of
156.7 events/s (p95 160.4). This number characterises the \emph{chosen
serialisation point in our prototype} -- a \texttt{FOR UPDATE} row lock
on \texttt{incident.state} -- and is \emph{not a protocol-level
throughput claim}. A different serialisation mechanism (sharded
incidents, per-incident leaders, append-only without state
materialisation) would shift this bottleneck. We report it to identify
where the serial cost lives, not to defend a throughput number.

\subsection{Command Journal Sequencing Evidence (M2)}
\label{sec:eval-m2}

M2's evidence is shared with M1 and M4. That writes commit at the command
authority is shown in Section~\ref{sec:eval-m1}; that sequencing remains
contiguous and non-forked across command transfer is shown by both the
model-level invariants and the service-path measurement in
Section~\ref{sec:eval-m4}. We do not duplicate those results here.

\subsection{Durable Outbox and Idempotency Evidence (M3)}
\label{sec:eval-m3}

This subsection reports evidence for M3 (durable outbox and idempotent
submission): propagation latency, WAN recovery, replay deduplication, and
behavior under emulated mesh impairment.

\textbf{Field-edit propagation.}
Field-edit propagation measures from the start of one or more
\texttt{POST /api/events} calls against the responder API until the command
database contains the expected rows in \texttt{incident.journal}. It
covers responder API handling, local outbox insertion, responder
\texttt{syncd} polling, command-side accept-and-sequence work, and
database commit. The result is approximately constant at queue depth
$\le 10$ (median $\approx 947$ ms) and rises to 1.22\,s at queue depth
100, reflecting the 250 ms responder-syncd poll interval, batch
processing on the command side, and a per-iteration TCP setup cost.

\textbf{WAN recovery.}
The WAN-recovery scenario, scoped in Figure~\ref{fig:partition-timeline},
isolates the command edge from the regional core and measures how long
committed command-journal rows take to appear in the core after the WAN
link is restored.
For 1\,s partitions the median recovery is 2.07\,s; for 10\,s partitions
5.79\,s; for 60\,s partitions 706\,ms (p95 2.73\,s). The non-monotonic
shape reflects implementation timers rather than partition duration alone:
the 10\,s cell pays the configured asyncpg \texttt{command\_timeout}, while
the 60\,s cell usually has discarded the broken connection before the link
heals. The protocol-level claim is therefore an empirical bound for this
implementation configuration, not a general network-recovery law. Summary
statistics for the propagation and recovery scenarios are in
Table~\ref{tab:evaluation}; the recovery distribution is plotted in
Figure~\ref{fig:recovery}.

\textbf{Empirical idempotency.} The duplicate-replay scenario
issues 50 unique \texttt{client\_event\_id} values and replays each five
times against a clean responder. The responder outbox and command journal
both enforce uniqueness on \texttt{client\_event\_id}; duplicates are
recognized and mapped to the existing command-side entry rather than being
assigned a fresh \texttt{event\_seq}. Across $n=30$ runs no replay produced
more than the 50 expected journal rows: \texttt{stored} equals
\texttt{unique\_events} in every run. The test exercises steady-state
idempotency over the emulated \texttt{syncd} accept-and-sequence path.

\textbf{Field-edit propagation under emulated mesh conditions.}
To take one step beyond the unimpaired Docker-bridge measurement, we
re-run the field-edit propagation scenario above with Linux \texttt{tc-netem}
qdiscs applied symmetrically on the responder and command \texttt{syncd}
container interfaces. Two link-condition profiles, informed by
published mesh-network measurements: \emph{stressed mesh}
(80\,ms~$\pm$~30\,ms delay, 2\,\% loss) and \emph{degraded mesh}
(200\,ms~$\pm$~80\,ms delay,
8\,\% loss)~\cite{zimbelman2022mesh,kumbhar2015legacy}. Each cell
runs 20 measurements at queue depths 1 and 10; all 80 cells
complete and no events are dropped. Table~\ref{tab:netem}
summarises the results.

The latency ordering is monotonic in both directions: at each queue
depth, degraded exceeds stressed; within each profile, queue depth
10 exceeds queue depth 1. Stressed mesh at queue depth 1 (median
1.21\,s) sits roughly 250\,ms above the unimpaired
$\sim$947\,ms baseline reported earlier in this subsection, consistent
with the 80\,ms one-way
delay applied to each direction plus occasional TCP retransmits at
2\,\% loss. The degraded queue depth 10 cell carries substantially
heavier tail latency (median 8.1\,s, p95 10.9\,s): an 8\,\% loss
rate inflates the tail because the probability of at least one
retransmit grows with the number of HTTP exchanges per cell.

\subsection{Fenced Promotion Evidence (M4)}
\label{sec:eval-m4}

This subsection reports evidence for M4 (fenced promotion): model-level
invariants under strict and weak promotion variants, and a service-path
measurement of fenced promotion under load.

\textbf{Formal model.} A TLA+ specification of the protocol's
authority machinery (single-writer journal, manual promotion, partition
state) is checked with TLC under bounded parameters $|V|=3$,
$\textit{MaxJournal}=2$, $|\textit{Cids}|=2$, with full symmetry over
vehicles. The specification supports two promotion variants controlled by a
single boolean. The strict variant requires that all current commands be
reachable from the candidate vehicle before a promotion proceeds; the weak
variant allows promotion regardless. Under the strict variant, TLC explores
$386$ distinct states at depth $10$ and finds no violation of any safety
invariant. Under the weak variant, TLC produces a
\textsf{SingleAuthority} counterexample at depth~$3$ (a single partition
followed by a promotion of the unreachable side). Suppressing role-level
invariants so search continues, TLC finds a \textsf{NoForkedJournal}
violation at depth~$5$ over $922$ explored states, with a trace that lands
the textbook split-brain pattern: partition, weak promote of the unreachable
side, both sides commit at $\textit{seq}=1$ with distinct
\texttt{client\_event\_id}s. The weak counterexample is not a defect of the
adopted system; it is a confirmation that the strict precondition encoded
in the manual promotion procedure is what makes \textsf{NoForkedJournal}
hold under the model. These bounds are intentionally small: the split-brain
witness at depth~5 shows that $\textit{MaxJournal}=2$ exposes the relevant
failure mode; $|V|=3$ admits a partition with majority, minority, and a
third observer; $|\textit{Cids}|=2$ distinguishes duplicates from distinct
events. The model does not cover storage crashes, fsync behavior,
certificate revocation, transport authentication, deployment
misconfiguration, operator mistakes, or physical compromise.
The model also checks \textsf{LocalIdempotency}, which is the model-level
counterpart of the M3 duplicate-replay evidence in
Section~\ref{sec:eval-m3}.

\textbf{Implementation-level testing.} A Hypothesis state-machine
test mirrors the TLA+ model in Python and exercises the same operations
under randomly generated schedules. Across 2000 examples of length~50, no
violation of \textsf{SingleAuthority}, \textsf{NoForkedJournal}, or
\textsf{LocalIdempotency} was found under the strict variant. A separate
test reproduces the weak counterexample by direct construction, confirming
that the simulator and the spec model the same abstract property. A small
smoke layer checks the idempotency path against the running prototype:
ten-fold replay of a single \texttt{client\_event\_id} produces exactly one
journal row, and five distinct ids produce five.

\textbf{Service-path fenced promotion.}
The service-level command-epoch enforcement closes the gap between the
model-level fenced-promotion evidence above and running-service behavior.
Migration~005 adds
\texttt{incident.command\_epoch} (monotonic \texttt{epoch\_id} per
operationally designated command vehicle) and stamps every
\texttt{incident.journal} row with the current epoch; the command
\texttt{syncd}'s \texttt{/accept/event-batch} handler reads
\texttt{X-Command-Epoch} from each request and accepts only when it
matches the running command's cached epoch, returning HTTP~409 with the
reason \texttt{stale\_epoch} (request behind) or \texttt{future\_epoch}
(request ahead).

We measure end-to-end behavior with
\texttt{scripts/evaluate-fenced-promotion.py}. Each of $n=5$ runs
issues three phases of 20 single-event POSTs against the command
\texttt{syncd}: (A) at the baseline epoch (current), (B) after
installing a new epoch row and restarting \texttt{syncd} so its cache
advances, replaying the now-stale baseline epoch, and (C) at the new
current epoch. The pre-registered acceptance invariants are
\texttt{duplicate\_seqs\_across\_epochs} ${=}~0$,
\texttt{stale\_epoch\_rejections} ${>}~0$, and
\texttt{new\_epoch\_commits} ${>}~0$, with contiguity within each
\texttt{command\_epoch}.

All five runs pass: phase~A commits 20/20 at epoch~1, phase~B
generates 20/20 HTTP~409 rejections at the stale epoch (zero events
land in \texttt{incident.journal} during this phase, by inspection of
the row count), phase~C commits 20/20 at epoch~2. Across the runs the
journal contains exactly 200 rows total (40 per run) split 100/100
between the two epochs, with no \texttt{event\_seq} value appearing
under both epochs and contiguous sub-sequences within each epoch.
Per-attempt commit latency medians are 6.3\,ms for phase~A and
5.7\,ms for phase~C; the stale-epoch rejection path (phase~B) returns
HTTP~409 in a median of 2.5\,ms, faster than the accept path because
the request is short-circuited before journal I/O.

This experiment is single-edge by design: each Rescue OIS edge owns
its own Postgres, so a cross-edge promotion exercises a different
shape of the property. The single-edge variant tests the
journal-poisoning invariant the paper actually claims: that
stale-epoch traffic cannot land in the journal at the current
command, even when replayed against a syncd that has just been told
about the promotion.

\subsection{Quorum-Progress Illustration}
\label{sec:eval-raft}

This subsection is included as a contextual quorum-progress illustration
and not as a workflow-equivalent baseline; see
Section~\ref{sec:protocol-m4} for why the authority-aligned design does
not adopt quorum-based promotion. A Raft cluster with $n=3$ voters and 2
voters isolated cannot commit by construction, as Raft requires by
design~\cite{ongaro2014raft}. We report this to motivate the design
choice of avoiding a quorum requirement at intermittently-connected
edges, not as a like-for-like comparison. Raft and Rescue OIS have
different progress dependencies (quorum availability versus
single-commander availability), different failure models, and different
operation classes. We deliberately do not compare latency or throughput
between them. The Raft runs use a 3-voter \texttt{hashicorp/raft}
cluster on the same Docker Compose substrate; full results are in
\texttt{paper/data/eval\_metrics\_raft.anon.jsonl} and summary
statistics in Table~\ref{tab:baseline}.

Under no partition the direct Raft leader path is faster than the
prototype's end-to-end field-edit path at queue depth~10 (median
10.5\,ms versus 946.3\,ms) because the baseline commits directly at the
leader without the responder outbox or syncd poll. After a 60\,s
isolation of one voter, the prototype's command-to-core recovery drain
(median 706\,ms) is shorter than Raft follower catch-up (median 4.1\,s)
on this substrate; the two paths measure different recovery mechanisms
and the numbers are reported for context only.

With two of three voters isolated, the Raft cluster commits 0 of 10
attempts throughout the partition window, as expected: a cluster with
$n$ voting members requires $\lfloor n/2 \rfloor + 1$ reachable voters,
so for $n=3$, losing two prevents progress. Rescue OIS imposes no
responder quorum, so command-local commits proceed during responder
isolation (20 of 20 in the partition run reported in
Section~\ref{sec:eval-m1}). This is the trade-off encoded in R3:
command-local write availability under responder partition at the cost
of automatic write failover.

\subsection{Measurement Threats to Validity}
\label{sec:eval-limits}

The measurements above are emulation results. Beyond the scope statements in
Section~\ref{sec:non-claims}, two measurement-specific threats apply:
WAN-recovery times are bounded by the configured \texttt{syncd} iteration
deadline and asyncpg \texttt{command\_timeout}, so the absolute recovery
numbers will shift under different deadline values; and the workload is
single-incident and limited-scale, with host hardware and container-runtime
metadata captured per-run in the artefact file but not varied as an
independent factor.
