\section{Authority-Aligned Architecture and Protocol}
\label{sec:architecture}

The requirements place conflicting demands on incident data. R1 and R2 require
local work and durable submission during disconnection; R3 requires one
authoritative order for command decisions. \systemname{} handles that split with
four mechanisms; M1 partitions state, M2 orders command writes, M3 carries
responder submissions, and M4 moves command authority without forking the journal.

\subsection{State Classes and Consistency Contracts (M1)}
\label{sec:state-taxonomy}

M1 sets the consistency boundary for R1, R2, and R3. Non-authority classes use
local/eventual contracts for R1 and R2; authority-bearing decisions use the
single-writer contract R3 demands. An operation crosses the linearization
boundary only when accepting concurrent versions would create an authority
conflict, like resource assignments, incident status transitions, and command hazard
annotations. These are accepted only by the command edge and inserted into the
incident journal with a command-assigned \textit{event\_seq}. 

This is the paper's
RedBlue-style partition~\cite{li2012redblue}; the ``red'' set is the
authority-bearing command decision stream, not the whole incident database.
Figure~\ref{fig:linearization-boundary} is the visual definition of M1, the
authority boundary follows command authority, not reachability or merge.

\begin{figure}[t]
\centering
\resizebox{0.9\columnwidth}{!}{\input{figures/fig_linearization_boundary}}
\caption{AAL linearization-boundary/state-class partition. M1 places the
single-writer authority boundary at the command edge: command decisions are
serialized into the incident journal by M2 with command-assigned
\textit{event\_seq}. Outside the boundary, reference/artifact data, responder
outboxes, and materialized views use local/eventual contracts for R1/R2; M3
forwards durable, idempotent field observations across the boundary, becoming
authoritative only after command acceptance. M4 moves the boundary by fenced
operator promotion, so the boundary is set by operational command rather than
Raft-style reachability or CRDT-style merge.}
\label{fig:linearization-boundary}
\end{figure}

Outside the boundary, edges still work while links are intermittent: reference
data are core-owned and cached, so partitions permit stale local reads, not local
redefinition, and immutable artifacts, audit records, and command-to-core backhaul
use validation or eventual forwarding rather than command-edge linearization.
Moving command authority requires the fenced-promotion rule of
\S~\ref{sec:protocol-m4} so a stale command edge cannot keep appending;

\subsection{Tiered Edge Topology}

Vehicle edges provide local services during disconnection; tablets are leaf
clients outside command sequencing (Figure~\ref{fig:tiered-topology}).

\begin{figure}[t]
\centering
\resizebox{\columnwidth}{!}{\input{figures/fig_tiered_topology}}
\caption{Tiered edge topology. The regional core holds master/reference data and
receives backhaul; vehicle edges run local services, with the command edge owning
the append-only incident journal and responder edges queuing submissions; tablets
are leaf clients. The mesh between vehicles is routed transit, not a consistency
mechanism, and user VLANs are not extended across vehicles.}
\label{fig:tiered-topology}
\end{figure}
