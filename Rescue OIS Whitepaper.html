01
01 — Executive Summary

A resilient information platform for the field

Rescue OIS is an offline-first incident information system for Swedish räddningstjänst operations. It replaces paper binders with a synchronized digital platform that remains fully operational when wide-area network connectivity is unavailable — the normal condition at many incident scenes.

The system is organized as three tiers: a regional core that manages authoritative master data (sites, plans, hazards, map tiles), vehicle edge nodes that host the incident journal and serve field tablets, and Android tablets carried by responders. All three tiers operate independently if network links are severed, then reconcile automatically when connectivity returns.

The central design choice is a single-writer incident journal on the command vehicle. Responder vehicles and tablets queue field edits locally and forward them to the command node — they never independently commit authoritative incident state. This trades some write availability for a dramatically simpler operational reasoning surface: there are no merge conflicts, no divergent timelines, no consensus rounds.

02
02 — Problem Statement

Paper binders and broken assumptions

Swedish rescue services (räddningstjänst) still depend on paper binders for pre-incident site plans, hazard registers, and operational reference material. These binders are resilient in a narrow sense — paper is available when networks fail — but they are difficult to update, impossible to search, and cannot synchronize across vehicles at an incident scene.

Existing digital alternatives introduce a different failure mode: they assume persistent connectivity to a central backend. At incident scenes, wide-area network coverage is unreliable. LTE coverage drops in industrial zones, basements, and rural terrain. Satellite uplinks add latency and complexity. When the backend is unreachable, a connectivity-dependent system fails entirely.

The operational requirements

The information problem for rescue services has specific structural properties that distinguish it from general-purpose collaboration:

  • Information must be authored at the station days or weeks before an incident, then transported into the field and available offline from the moment of dispatch.
  • Incident-level updates (status changes, hazard notes, resource assignments) must be operationally coherent across all vehicles at the scene — a wrong merge is worse than a delayed one.
  • The command structure is hierarchical, not flat. There is always a designated incident commander. Authority-bearing updates flow through that role.
  • Hardware must be deployable in existing vehicles without specialized networking infrastructure at the scene.
The key insight: this is not a general offline-first problem. It is a command-hierarchical, authority-bearing information problem where sequence integrity matters more than write availability at leaf nodes.

03 — System Architecture

Three tiers, one writer

Rescue OIS is structured as three tiers. Each tier operates independently when disconnected from the tier above it, and resynchronizes when the link returns. The critical constraint is that only one node — the command vehicle's K430 — writes to the incident journal at any time.

Design principles

Five invariants govern every component in the system: offline-first (all previously synchronized data remains available without connectivity); single incident writer (only the command K430 sequences and commits incident events); forward-only edits (tablets and responder vehicles enqueue edits locally and forward them upstream, never committing directly); mesh as transit only (the Rajant mesh carries inter-K430 traffic but user VLANs are never stretched across it); and existing identity (the deployment integrates with the authority's established certificate infrastructure).

04
04 — Synchronization Protocol

Six flows, one direction of authority

Rescue OIS defines six distinct synchronization flows. Each has a specific transport, mechanism, direction, and failure behavior. The flows are asymmetric by design: master data flows outward from the core, incident state flows inward toward the command vehicle, and the command vehicle forwards the authoritative journal to the core for archival.

1
Core → Vehicle Baselinecontinuous + 15 min poll
PostgreSQL logical replication for master tables (sites, plans, hazards, area geometries), plus HTTP polling of manifest.json for PMTile packages and attachment downloads via HTTP range requests. Edge keeps the last known good package; replication catches up automatically when the WireGuard link returns.
WireGuard · HTTPS · core → edge
2
Incident Bootstrapon dispatch
GET /sync/bootstrap?incident_id=… returns AOI geometry, plan references, hazard subset, and attachment list. Command K430 marks itself as writer of incident.journal and incident.state. If core is unreachable, the command vehicle bootstraps from cached master data and reconciles later.
WireGuard · HTTPS · core → command
3
Tablet → Vehiclebidirectional, local
Read: GET /api/bootstrap, /api/search, /tiles/*, /files/*. Write: POST /api/events with a FieldEdit body including a client-supplied client_event_id UUID for idempotency. Tablets maintain a local Room outbox and retry until the K430 acknowledges.
OPS-TABLET VLAN · HTTPS · bidirectional
4
Responder → Commandforward-only, mesh
syncd.push on responder K430s batches rows from outbox.device_outbox (where forwarded_at IS NULL) and HTTP POSTs them to the command K430's accept endpoint. The command assigns monotonic event_seq values and persists events into incident.journal. The responder marks rows forwarded once acked.
Rajant mesh · HTTPS · responder → command
5
Command → Coreincremental, buffered
syncd.forward posts incremental journal slices keyed by event_seq to the core sync-api. Core acks with the last accepted sequence number. The command edge buffers locally and resumes from the last acked sequence when the WireGuard link returns.
WireGuard · HTTPS · command → core
6
Failure / Recoverymanual promotion
If the command vehicle is lost, responder K430s detect absence via heartbeat timeout. An operator runs promote-responder.sh on a designated responder — EDGE_ROLE flips to command and syncd restarts. Every promotion is logged by audit-forwarder with the operator identity. The new command reconciles its local journal by event_seq.
manual · mesh + WireGuard · recovery
Why not CRDTs? CRDT-friendly designs require application-level semantics for resolving conflicting authority-bearing updates. Incident state contains command decisions, ordered status transitions, and resource assignments whose meaning is sequence-dependent. The single-writer design intentionally trades write availability at responder nodes for a smaller operational reasoning surface. In this domain, that is a feature, not a defect.

05 — Security Model

Layered isolation at every boundary

The security model has three layers: network segmentation enforced by the RUTX50 firewall, mutual TLS authentication at every API boundary, and WireGuard for encrypted transport between vehicles and the regional core.

Per-vehicle VLAN segmentation (RUTX50)

Each vehicle uses 172.31.<vehicle_id>.0/24 carved into five VLANs. The vehicle ID octet is unique per vehicle. User VLANs are never stretched across the Rajant mesh — the mesh carries only inter-K430 application traffic.

Firewall enforcement (key rules)
  • Tablets (VLAN 30 OPS-TABLET) may only reach the K430's ops-api over HTTPS. No mesh access, no internet, no lateral movement to other tablets.
  • Only EDGE-SVC (the K430) may initiate outbound connections to the WireGuard overlay and the Rajant mesh.
  • Sensors (VLAN 40) may only POST to a dedicated EDGE-SVC ingest port over TLS.
  • The MAINT VLAN has no path to EDGE-SVC, OPS-TABLET, or the mesh — it is SSH-only to MGMT.
mTLS authentication (planned)

Tablets authenticate to the K430 ops-api via mTLS client certificates issued by the organizational CA. The K430 server certificate is pinned in the tablet trust store (Knox Manage). Edge-to-edge and edge-to-core communication uses the same CA. require_tablet_identity() and require_edge_identity() in the codebase are currently stubbed pending CA integration.

Implementation status. mTLS enforcement is designed and scaffolded but not yet active. The Nginx mTLS client verification block is commented out in the current edge configuration. Certificate paths are placeholders. This must be resolved before any production deployment.

06 — Deployment Requirements

Hardware stack per vehicle

Each rescue vehicle in the fleet requires three hardware components: a K430 edge computing node running the Docker Compose service stack, a RUTX50 router enforcing VLAN segmentation and firewall policy, and one or more Rajant Hawk mesh radio units providing the inter-vehicle transit network. Tablets are ruggedized Android devices enrolled via Knox Manage.

What the simulation does cover

The simulation validates the structural correctness of the synchronization flows: that the outbox queuing and forwarding mechanism works, that event sequences are monotonically assigned, that partition injection and recovery follow the expected state machine, and that the promotion procedure transitions the node into command mode cleanly. These properties hold in the simulation; whether they hold at physical pilot scale remains to be demonstrated.

What it does not cover
  • Real Rajant mesh latency and packet loss under operational RF conditions
  • LTE coverage variability across Swedish incident terrain types
  • Multi-incident concurrency at the regional core
  • Tablet battery and performance under sustained offline use
  • Sustained offline usability duration and data staleness under long partitions

08 — Limitations & Known Gaps

What this design does not solve

The following limitations are architectural properties of the current design, not implementation oversights. They should be communicated clearly to any adopting organization.

Architectural limitations
  • Command node is a temporary single point of failure. Until promotion is complete, the incident journal cannot accept new committed events. Responder outboxes queue, but no new sequences are assigned.
  • Promotion is manual and operator-driven. Running promote-responder.sh requires an operator at the vehicle or remote SSH access. There is no automatic failover. This was a deliberate choice — automatic promotion in a command-hierarchical context raises operational authority questions that require human judgment.
  • Polling-based synchronization adds bounded latency. The 15-minute master-data poll and syncd polling intervals add predictable but real delays. This is acceptable for master data; it is tighter for incident events but not real-time.
  • Pilot scale only. The simulation uses a single core, two edge nodes, and a small number of tablets. Behavior under very large fleets or concurrent multi-incident operations is unknown.
Implementation gaps (current prototype)
  • All microservice business logic raises NotImplementedError. No actual synchronization data flow is implemented.
  • mTLS enforcement is stubbed — require_tablet_identity() and the Nginx client verification block are placeholders.
  • PostgreSQL logical replication is not configured — no publications, subscriptions, or replication slots exist in migrations.
  • Ansible roles contain only placeholder debug tasks.
  • The Room AppDatabase entity list is empty; DAOs have no @Query methods.
  • Evaluation metrics are from two separate hardcoded sources that do not agree with each other.
These gaps are documented honestly in the repository's mismatch.md. The contribution of the current prototype is an architectural pattern and reference scaffold — a well-structured foundation for an implementation team, not a deployable system.
09
09 — Conclusion & Next Steps

A tractable path to the field

Rescue OIS demonstrates that an offline-first, command-hierarchical information system for rescue services is architecturally tractable without consensus protocols, multi-writer conflict resolution, or continuous cloud connectivity. The single-writer incident journal is a strong simplification that matches the operational reality: there is always a designated incident commander, incident state is authority-bearing, and a wrong merge is worse than a delayed one.

The three-tier architecture maps cleanly onto the real operational hierarchy — regional core, vehicle fleet, field tablets — and each tier degrades gracefully under the specific failure modes that occur at real incident scenes: WAN loss, mesh-only conditions, and total isolation of individual vehicles.
