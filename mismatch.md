# Paper vs. Repository Mismatches and Remaining Issues

## Critical Mismatches

### 1. "Pilot Deployment" vs. Docker Simulation
The abstract and introduction describe "a controlled pilot deployment" and claim evaluation results from a real deployment. In reality, the evaluation is a **Docker Compose simulation** with **mock latencies** injected by `evaluate-pilot.py`. The `inject-partition.sh` script currently just sleeps rather than actually disconnecting Docker networks. The bootstrap latency (1000ms), field edit propagation (~100ms per event), recovery time (1200ms), and promotion latency (2500ms) are **hardcoded mock values**, not measured from a real system.

**Recommendation:** Either conduct an actual pilot, or reframe the evaluation honestly as "emulated deployment" / "simulation-based evaluation" throughout the paper.

### 2. Business Logic Is Entirely Stubbed
All microservice business logic raises `NotImplementedError`. The `sync-api` returns mock data, `ops-api` routes return 501, `syncd` sync flows are unimplemented, the publisher pipeline is stubbed, and all feed importers are empty. The paper's Section 5 (Implementation) presents the system as "an implemented artifact, not merely an architectural proposal" but **no actual synchronization, data flow, or incident management logic exists**.

**Recommendation:** Either implement the core sync flows (at minimum: `syncd` push/accept/forward and `ops-api` bootstrap/events) before claiming implementation, or explicitly state that the contribution is an architectural design with a reference scaffold.

### 3. Abstract Mentions Metrics Not Actually Measured
The abstract lists "offline survivability" and the evaluation metrics section planned to measure "sustained offline usability duration" and "data staleness under partition." Neither metric is captured by `evaluate-pilot.py` or logged in `eval_metrics.log`.

**Recommendation:** Either add these measurements or remove the claims from the abstract.

### 4. Evaluation Numbers: Paper vs. Actual Mock Data
The paper's result table previously showed approximate values (~1.1s, ~250ms, ~1.2s, ~2.5s). The actual `generate_plots.py` uses fallback mock arrays: bootstrap median 1075ms, edit propagation median 255ms (from [230,255,248,262,241]), WAN recovery 1250ms, promotion 2550ms. Meanwhile `evaluate-pilot.py` logs exact round numbers (1000ms, 100ms, 1200ms, 2500ms). These are **two different sets of mock values** that don't agree with each other.

**Recommendation:** Unify the evaluation data pipeline so there is one authoritative source of truth for all numbers cited in the paper.

## Moderate Issues

### 5. PostgreSQL Logical Replication Not Configured
Section 4 (Sync Protocol) and docs/architecture/sync-protocol.md describe "PostgreSQL logical replication" for Flow 1 (core-to-edge master data sync). No logical replication configuration exists in the repository — no publications, subscriptions, or replication slots are defined in any migration or config file. The actual `syncd/pull.py` is stubbed.

**Recommendation:** Either implement the logical replication setup in migrations/config, or reframe Flow 1 as HTTP-based polling (which is what the stub code structure suggests).

### 6. mTLS Authentication Entirely Stubbed
The security model describes layered mTLS authentication (tablet-to-edge, edge-to-edge, edge-to-core). In the code, `require_edge_identity()` and `require_tablet_identity()` are empty stubs. The Nginx mTLS client verification block is commented out in the edge config. TLS certificates are placeholder paths.

**Recommendation:** Note this as "planned but not yet deployed" in the implementation section rather than presenting it as implemented.

### 7. Ansible Roles Are Empty
All four Ansible roles (postgres, martin, nginx, wireguard) contain only TODO placeholder debug tasks. The provisioning playbooks reference these roles but would not actually provision anything.

**Recommendation:** Either implement the roles or describe infrastructure provisioning as "template-based" rather than "automated via Ansible."
